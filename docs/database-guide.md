# database-guide.md — how to look at, and query, scw.db

The database is **SQLite in WAL mode**, one file: `scw.db` at the project
root (path is `backend/config.py::DB_PATH`, override with the `SCW_DB` env
var). WAL mode means you'll also see `scw.db-wal` and `scw.db-shm` next to
it while the backend is running — that's normal, not corruption. All three
files matter: if you ever copy the database out for a backup, copy all
three, or checkpoint first (see "Gotchas" below).

Everything that reads or writes it goes through `backend/db.py`, and every
multi-row mutation runs inside one `backend/db.py::transaction()` (see
`backend/warehouse.py`). Nothing in this project uses an ORM — it's seven
tables and plain SQL, on purpose, so it stays readable at 3 a.m. before a
demo. Six of those tables carry the live system; the seventh (`meta`) holds
the simulated-clock checkpoint (see §1).

---

## 1. The schema

```
articles(ref PK, label, unit_mass_g, tolerance_g, cure_floor_h,
         len_mm, wid_mm, h_mm, holes, color)
boxes(box_id PK, article_ref FK->articles NULL, qty_initial, qty_available,
      slot_id FK->slots, state, t_in_sim, required_cure_h, ready_at_sim,
      count_beam, count_weight, gross_g, confidence, reason,
      locked_by, lock_expires_sim, code, batch_id, vision_ref, id_confidence)
slots(slot_id PK, face, col, level, occupied_by, reserved_for)
orders(order_id PK, ref, qty_requested, qty_allocated, status, created_sim, payload)
events(id PK AUTOINCREMENT, t_sim, kind, payload)
meta(k PK, v)
barcodes(barcode_id PK, ref FK->articles, unit_mass_g, registered_sim, used_by_box)
```

| table | what a row is | who writes it |
|---|---|---|
| `articles` | one noyau reference (its ground-truth unit mass and tolerance, plus a shape signature for the simulated vision station — no capacity, contract 1.6) | `db.seed()` on boot/reset (the four demo refs), plus `POST /api/articles` any time the dashboard's "+ New reference" form (⋯ menu) or a script adds one — see §1b |
| `boxes` | one physical crate of cores, tracked through its whole life | `backend/warehouse.py::create_box` (creation), and every other function in that module (reserve/confirm/cancel/sweep_expired/sweep_cured/produce_for_batch) as it moves through its life |
| `slots` | one of the `FACES x COLS x LEVELS` rack cells (see `backend/config.py`) | generated by `db.seed()`; `occupied_by`/`reserved_for` updated as boxes move, always in the same transaction as the box |
| `orders` | one production demand and the FIFO plan that answered it | `backend/warehouse.py::reserve` (creation), `confirm`/`cancel`/`sweep_expired` (status + payload.status) |
| `events` | append-only log — every mutation above also writes one row here, in the SAME transaction | throughout `backend/warehouse.py` and `backend/main.py::event()`, via `db.log_event` |
| `meta` | key/value store for the simulated-clock checkpoint | `db.seed()` resets it (`t_sim`, `speed` back to their config defaults); `backend/warehouse.py::checkpoint_clock` updates it on every mutation and every ~5 real seconds from `loop_clock`; `restore_clock` reads it on backend startup |
| `barcodes` | one physical box's traceability label — a worker's registration, made before that box ever arrives (CDC step 1) | `backend/warehouse.py::register_barcode` (creation, `POST /api/barcodes`); `create_box` sets `used_by_box` the instant the conveyor's scanner reads it back |

**Relationships**, including the two that aren't real foreign keys:

- `boxes.article_ref -> articles.ref` — real FK, **nullable**. Every box holds cores of exactly one reference, except a box quarantined for an *unrecognised or already-used* barcode, which has `article_ref = NULL` (or, for a reused barcode, the reference it WAS registered against — see `reason`). A partial unique index (`uq_boxes_slot`, `WHERE slot_id IS NOT NULL`) additionally guarantees a slot is never claimed by two boxes.
- `boxes.slot_id -> slots.slot_id` — real FK, nullable (NULL while `QUARANTINE` with no free slot, or a fully-picked `EMPTY` box).
- `slots.occupied_by -> boxes.box_id` — **soft** back-reference, but not unconstrained: a partial unique index (`uq_slots_occupied`, `WHERE occupied_by IS NOT NULL`) guarantees one box per slot at the DB level, and it is updated in the *same transaction* as `boxes.slot_id` (`backend/db.py::transaction`), so the two can never observably disagree.
- `slots.reserved_for -> orders.order_id` — soft; set while a pick is `RESERVED`, cleared on confirm/cancel/expiry — genuinely maintained now (contract 1.2; it previously was not, see the Gotchas below).
- `boxes.locked_by -> orders.order_id` — soft; the lock owner, set/cleared alongside `slots.reserved_for`. `backend/consistency.py` check `S4` cross-checks the two agree.
- `orders.payload` — the full FIFO plan (`picks[]` / `rejected[]`) as a JSON blob, not normalized into rows, captured once at reserve time. `payload.status` is kept equal to the `status` column on every write, so either can be trusted.
- `events.payload` — JSON blob too, shape depends on `kind` (see `docs/contracts.md` for the event kinds that matter).
- `boxes.code` — the `barcode_id` the conveyor's scanner actually read off this physical crate (contract 1.5). Unlike a shared article `ref`, a barcode is a single physical box's own registration (`backend/warehouse.py::register_barcode`) and carries its OWN measured `unit_mass_g` — that value, not the article's average, is what `assess_box` divides the scale reading by.
- `barcodes.ref -> articles.ref` — real FK. A worker declares which reference a physical box holds when registering its barcode, well before it ever arrives.
- `barcodes.used_by_box -> boxes.box_id` — soft; NULL until the conveyor's scanner reads this barcode back (`create_box`), at which point it's set once and never cleared — a barcode is consumed exactly once, accepted or quarantined. A second scan of the same barcode is quarantined as `"code-barre deja utilise"` rather than treated as a second physical box.
- `boxes.batch_id -> orders.order_id` — soft; contract 1.6. Set when a box is produced to cover a demand that existing stock couldn't (`backend/warehouse.py::produce_for_batch`), NULL for ordinary stock added independently of any order. `backend/consistency.py` check `O4` catches an orphaned reference; check `O5` catches a batch box ever being `RESERVED` by a different order (`algo/engine.py::fifo_allocate` excludes `batch_id` boxes from general stock entirely, contract 1.7).
- `boxes.vision_ref` / `boxes.id_confidence` — contract 1.7. The reference the simulated vision station's shape reading matched (`algo/engine.py::identify_core`) and how confident that match was, independent of the barcode. NULL when no vision reading was taken for this arrival (the manual "quick box" shortcut) — identification then rests on the barcode alone, as it did before 1.7.

This same list lives as data (not prose) in `backend/dbview.py::RELATIONS`, which is what the DB Explorer renders — if this file and that list ever disagree, trust `dbview.py` and fix this file.

### 1b. `articles` grows after seeding — it isn't a fixed lookup table

`db.seed()` loads the four demo references (`backend/db.py::ARTICLES`) into
`articles`, but that's the *initial* content, not the *only* content.
`POST /api/articles` (`backend/db.py::add_article`, contract in
`docs/contracts.md` §2) inserts additional rows at any time — this is what
backs the dashboard's "+ New reference" form. `ref`, `label`, `unit_mass_g`
are required; `tolerance_g` defaults to ~3 % of the unit mass; `color`
defaults to the next unused swatch in a fixed palette (`backend/db.py::
NEW_REF_PALETTE`) so two references never collide on colour by accident.
There is no `box_capacity` to set (contract 1.6 removed it — nobody knows
how many cores are in a box ahead of time, that's what the scale is for).
`cure_floor_h` is always `backend/config.py::CURE_H` (24.0) regardless of
what the request sends — contract 1.2 fixes drying at 24 h for every
reference, so this field cannot be overridden per-reference any more. A
duplicate `ref` or a non-positive `unit_mass_g` is rejected before it
reaches the table.

A row added this way lives only in `scw.db` — the next `POST /api/reset`
(with the default `{"seed": true}`, or no body) or `python -m backend.db`
wipes it back down to the four seeded references, same as any other table.
`POST /api/reset {"seed": false}` wipes boxes/orders/events/slots but
*keeps* whatever is currently in `articles`, including rows added this
way — use that variant if you want the reference to survive a mid-demo
reset without editing a file. If you want it to survive `python -m
backend.db` too (e.g. you're adding a permanent fifth product line, not
testing), add a tuple to `ARTICLES` in `backend/db.py` instead —
everything downstream (dropdowns, FIFO, the 3D twin) reads articles from
the table at runtime either way, so neither path needs any other file
changed.

### State machines to know before you read `boxes`/`orders`

```
boxes.state (persisted):  (birth) -> DRYING -> READY -> RESERVED -> READY (cancel/expiry, t_in_sim unchanged)
                             |         ^                          -> EMPTY (confirm, always whole-box, 1.9) -> ARCHIVED
                             v         | successful recount (contract 1.7,
                        QUARANTINE ----+ t_in_sim re-stamped to the recount time)
                             |
                             -> ARCHIVED

orders.status:  (birth) -> PENDING -------> DONE
                        \                -> CANCELLED  (explicit cancel, or an
                         \                              expired reservation --
                          \                             event kind order_expired)
                           -> IN_PRODUCTION -> DONE       (batch shipped, once
                           |                               none of its boxes
                           |                               is still DRYING)
                           |                -> CANCELLED  (batch_id cleared on
                           |                               its boxes)
                            -> IMPOSSIBLE
```

A box is born directly into `DRYING` or `QUARANTINE` — `INCOMING`,
`IDENTIFYING`, `COUNTING`, `STORING` and `PICKING` are **virtual** stages:
real moments (narrated in `box_in`'s evidence and `pick_done`'s per-box
detail in the `events` table) that are never written to `boxes.state`. If
you `SELECT DISTINCT state FROM boxes` and only ever see `DRYING`,
`READY`, `RESERVED`, `EMPTY`, `QUARANTINE`, `ARCHIVED` — that is correct,
not a bug. See `algo/engine.py`'s `PERSISTED_STATES` / `_TRANSITIONS`.

Three rules that will save you time when a query result looks "wrong":

1. **There are no wall-clock timestamps anywhere.** `t_in_sim`, `ready_at_sim`, `created_sim`, `t_sim`, `lock_expires_sim` are all simulated seconds from `backend/config.py::CLOCK_START_SIM`, not `datetime.now()`. Don't try to correlate them with real time. (`meta`'s clock checkpoint and device-liveness checks use `time.monotonic()` in backend runtime memory only — never a value that lands in one of these columns.)
2. **A pick is WHOLE-BOX-ONLY** (contract 1.9, reversing 1.7's partial picks) — `take` is always a candidate box's entire `qty_available`, so confirming a reservation always empties every box it touched (`state` -> `EMPTY`), even when that overshoots what was actually requested. A query expecting a picked box to sometimes stay `READY` with a partial remainder after confirm is checking a rule that no longer holds.
3. `required_cure_h` is `24.0` on every box, unconditionally — there is no adaptive model in this system (contract 1.2), and no climate sensor left to feed one even in principle (contract 1.8 removed the DHT22).
4. `IN_PRODUCTION` (contract 1.6) only happens when the ENTIRE pipeline for a reference — including boxes still `DRYING` or `RESERVED`, not just currently-free ones — can't cover a demand. If enough already exists somewhere, just not free yet, the order stays the ordinary `IMPOSSIBLE` refusal it always was. `backend/warehouse.py::reserve` makes that call; `boxes.batch_id` (not `orders.payload.picks`, which stays empty for a batch) is the authoritative link between a batch order and what was produced for it. A box tagged to one batch is never visible to a different demand's `fifo_allocate` call (contract 1.7) — it is not general stock.
5. Quarantine is not necessarily final (contract 1.7): `POST /api/box/{id}/archive` closes a `QUARANTINE`/`EMPTY` box out for good, and `POST /api/box/{id}/recount` re-presents a `QUARANTINE` box's evidence (a re-weigh, optionally a fresh vision reading) and, on success, sends it back through `DRYING` from `t_in_sim = now` — same barcode, same physical box, no second row created for it.

## 2. Three ways to look at it

### A. The built-in DB Explorer (easiest, read-only, no setup)

With the backend running, open **`http://localhost:8000/db`**. It's a small
page (`dashboard/db.html`) backed by a read-only JSON API mounted at
`/api/db/*` (`backend/dbview.py`):

| endpoint | returns |
|---|---|
| `GET /api/db/schema` | columns, types, FKs (from `PRAGMA`) + the relations table above |
| `GET /api/db/tables` | the 5 *active* table names with row counts (`meta` is excluded from the table browser — it's whitelisted out in `dbview.py::TABLES`, but it is no longer empty: see §3) |
| `GET /api/db/table/{name}?limit=&offset=&q=` | paged rows, newest first, `q` does a substring search across the text columns |
| `GET /api/db/stats` | boxes by state, stock by reference, the full slot grid, event count, orders by status |
| `GET /api/db/check` | the consistency checker (`backend/consistency.py`) — `{"overall":"PASS"\|"WARN"\|"FAIL", "checks":[...]}` over 25 checks; shown as a badge at the top of the page |
| `GET /api/db/box/{id}` | one box's row + slot + every event/order that names it — click a `box_id` in the table browser (while viewing `boxes`) to open this |

It is enforced read-only at the driver level (`PRAGMA query_only = ON` on
every connection it opens) — useful when you want to poke around during a
live demo without any risk of changing what the jury sees. It never creates,
edits, or deletes a row; that stays the job of `backend/warehouse.py`'s
transactional operations, called from `main.py`'s REST endpoints.

### B. `sqlite3` CLI, straight against the file

Good for ad-hoc questions and for scripting checks in CI/test scripts. Since
it's WAL mode, you can read with the server running — WAL is specifically
designed for concurrent readers alongside one writer, so this is safe:

```bash
sqlite3 scw.db
```

```sql
.headers on
.mode column
.tables                                   -- list the 5 tables
.schema boxes                             -- full CREATE TABLE for one table

SELECT box_id, article_ref, state, slot_id, qty_available FROM boxes;

SELECT * FROM slots WHERE occupied_by IS NULL LIMIT 5;   -- free slots

SELECT article_ref, count(*) FROM boxes GROUP BY article_ref;  -- boxes per article
                                                          -- (article_ref, not ref -- boxes has no `ref` column)

SELECT * FROM events ORDER BY id DESC LIMIT 20;          -- recent activity
```

Don't `UPDATE`/`DELETE` by hand while the backend is running — it has no
idea you touched the file and its in-memory `STATE` (crane, clock) will
drift from what's on disk. `backend/db.py::transaction()` opens with `BEGIN
IMMEDIATE`, so a hand-run `UPDATE`/`DELETE` that overlaps a backend write
will simply block until the backend's transaction commits (WAL mode allows
one writer at a time) rather than corrupt anything — but it will still
leave the backend's runtime `STATE` unaware of your change. If you need to
change data, use the REST API (`POST /api/reset`, `/api/sim/box`, etc. —
see `docs/contracts.md`) so the backend's broadcast stays consistent with
the row you changed, then check `GET /api/db/check` afterward if in doubt.

### C. Python, using the project's own helpers

Best when you want to reuse the exact same row-shaping the backend uses
(`sqlite3.Row` -> `dict`), e.g. from a REPL or a one-off script:

```python
from backend import db as DB

con = DB.connect()                                    # scw.db, WAL, FK-enforced
boxes = DB.rows(con, "SELECT * FROM boxes WHERE state = ?", ("DRYING",))
one_box = DB.one(con, "SELECT * FROM boxes WHERE box_id = ?", ("BOX-1",))
```

`DB.rows()` / `DB.one()` are the same helpers `backend/main.py` uses
everywhere, so query results come back as plain dicts, not `sqlite3.Row`
tuples.

## 3. Resetting / reseeding

The `slots` table's row count is derived from `backend/config.py`
(`FACES x COLS x LEVELS`), not hand-maintained — if you change the rack
geometry, the next seed regenerates `slots` to match.

```bash
POST /api/reset          # via the REST API — wipes + reseeds, updates the
                          # backend's in-memory STATE too (the right way to
                          # do this while the server is running)

python -m backend.db     # or run db.py directly: connects, creates tables
                          # if missing, and seeds fresh. Prints the slot/
                          # article counts it just wrote. Use this when the
                          # server isn't running (e.g. before first boot).
```

`db.seed()` wipes `boxes`, `orders`, `events`, `slots`, `articles`, and
`meta` (in that order, for FK safety), rebuilds `slots` + `articles` from
scratch, and resets the `meta` clock checkpoint to
`backend/config.py::CLOCK_START_SIM`/`DEFAULT_SPEED` — the whole thing runs
as one transaction (`backend/db.py::transaction`), so a crash mid-seed
cannot leave a rebuilt `slots` table next to a half-cleared `boxes` table.
`seed(con, keep_articles=True)` (the contract's `POST /api/reset
{"seed": false}`) skips the `articles` wipe/rebuild, so a reference added
at the venue via "+ New reference" survives.

## 4. Gotchas

- **Foreign keys are enforced** (`PRAGMA foreign_keys=ON` in `db.connect()`). A
  raw `INSERT` into `boxes` with a bad `article_ref` or `slot_id` will raise,
  not silently create an orphan row.
- **Backing up**: `scw.db` alone can be missing recent commits that are
  still sitting in `scw.db-wal`. Either copy all three files together, or
  checkpoint first: `sqlite3 scw.db "PRAGMA wal_checkpoint(FULL);"` then copy
  just `scw.db`.
- **`orders.payload` / `events.payload` are JSON text**, not JSON columns —
  filter on them with SQLite's `json_extract(payload, '$.field')`, or just
  pull the row and `json.loads()` it in Python; don't expect a normal `WHERE
  payload.field = ...`.
- **The DB Explorer is a mirror, not a second brain.** If `dbview.py`'s
  hand-written `RELATIONS` list and the live `PRAGMA` output it also shows
  ever disagree, that's a bug in this file or in `db.py`'s schema — file it
  as such rather than trusting whichever one you saw first.
- **`meta` is no longer always empty.** It holds exactly two rows,
  `k='t_sim'` and `k='speed'` — the simulated-clock checkpoint
  (`backend/warehouse.py::checkpoint_clock`/`restore_clock`). Both are
  reset by every `db.seed()`. Nothing else uses `meta`.
- **When something looks wrong, run the checker before you start
  debugging by hand:** `GET /api/db/check` (or `python -m
  backend.consistency` with the server stopped) runs 22 read-only checks
  and tells you exactly which invariant broke, with the offending row ids
  — usually faster than reconstructing the bug from a raw table dump.
